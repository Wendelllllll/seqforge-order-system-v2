# SeqForge 线上测试站、GoDaddy 与设计交接

更新：2026 年 11 月 1 日。本文记录已经完成的部署与当前边界；技术命令、镜像摘要和恢复步骤见[英文运维手册](README.md)。

## 现在从哪里访问

网站入口是 **[https://seqforgebio.com](https://seqforgebio.com)**，`www.seqforgebio.com` 自动跳转到同一入口。登录后可使用客户功能，获授权的管理员通过 `/admin` 进入后台。

网站已经运行在 AWS，不需要开发电脑保持开机。指定的真实账号已完成注册、邮箱验证和管理员授权；授权后原会话已注销，需要重新登录。首次重新登录后的管理员界面操作仍需用户确认。不要把本地演示账号当成云端账号。

| 部分 | 负责什么 |
| --- | --- |
| GitHub | 前台、后台、API、数据库迁移、测试与部署说明的源码版本 |
| GoDaddy | `seqforgebio.com` 的域名和 DNS 解析，告诉浏览器服务器在哪里 |
| AWS Lightsail | 运行 Next.js 应用、HTTPS 代理和私有结果文件存储 |
| AWS 托管 PostgreSQL | 保存账号、订单、价格、状态和结果文件元数据 |
| 独立 SMTP 服务 | 发验证、订单、结果和内部提醒邮件；配置单独保存在服务器 |

**GitHub push/合并目前不会自动发布网站。** 设计伙伴提交代码后，还需要维护人员执行一次明确的 AWS 发布流程。无需在 GoDaddy 上传网站文件，也不需要为了这套部署另买 GoDaddy 网站主机。

| 管理后台 | 订单搜索筛选、客户资料/历史订单、全局及单个客户专属测序价格、历史价格快照 |

| 订单与测序结果 | Needs attention 原因/处理记录；上传并检查测序结果后由管理员明确完成，客户才能下载并收到结果就绪通知 |
| 账号与邮件 | 邮箱验证、密码找回、订单确认、内部新客户/新订单提醒；真实注册和验证已完成一次 |

Excel 的 **`.xlsx` 工作簿上传不支持**，请复制单元格或导出 CSV。草稿只在对应浏览器/账号中恢复，不跨电脑同步。未提交的草稿不会进入管理员订单列表。服务介绍页的 sample planner 已移除。

以下不能视为已完成：完整的 Oligo 报价批准/生产流程、自动 LIMS/仪器对接、信用卡收款和自动开票。Oligo 特殊规格仍需人工报价。结果文件支持每单一个文件或压缩包、上限 25 MB；上传与发布是不同步骤。客户邮件的持续重试/故障恢复任务尚未完善，现有 `mail:status/flush/retry` 工具只管理内部通知。

线上已检查首页、三类表单、价格显示和 Dropbox 地图/地点选择；这不等于每项业务的真实订单、密码重置、结果交付已经全部验收。数据库和结果文件的备份恢复演练也尚未完成。指定邮箱已收到并完成账号验证；另一次内部 setup 测试只有 SMTP 接受成功的记录，其单独收件确认仍待核实。

## GoDaddy 是怎样接到 AWS 的

以下是已经配置好的 **seqforgebio.com** 记录，无需为了本次代码更新再次修改：

| 类型 | 名称 | 内容 | TTL |
| --- | --- | --- | --- |
| A | `@` | `44.240.100.124` | `600` 秒 |
| CNAME | `www` | `seqforgebio.com`，即主入口 | 保留原有值 |

在 GoDaddy 的 Domain Portfolio 选择 **seqforgebio.com → DNS**，即可检查这些记录。需要修复时编辑现有 `@` 记录，不要额外添加相互竞争的 A 记录；IP 内容不带 `https://` 或路径。`www` 保留指向主入口。若域名的权威 nameserver 在其他服务商，必须到实际 DNS 服务商操作。[GoDaddy 官方操作说明](https://www.godaddy.com/en-uk/help/add-or-edit-an-a-record-42546)说明了当前界面和传播时间；TTL 600 是缓存时间，不保证全球恰好十分钟生效。

浏览器得到 AWS 静态 IP 后，通过 Caddy 进入 Next.js 应用。Caddy 已自动取得 HTTPS 证书并负责续期，www 以 308 跳转到主入口且保留路径/查询参数。正常发布新版本不需要更改 DNS，也不需要单独购买 GoDaddy SSL。

**不要把这张表套用到 `seqforge.com`。** 原网站、公司邮箱、MX、TXT、mail/webmail 记录和 nameserver 均保持原样。11 月 1 日复核时，旧主域的 MX 目标正是 **seqforge.com 本身**，所以只改主域 A 记录，也可能把收件引向新的 AWS 网站服务器，即使 MX 本身没改。将来正式切换主域前，应一起核对 MX 目标的 A/AAAA、SPF、DKIM、DMARC 和邮箱入口，单独规划网页与邮件解析。网站服务器迁走，不等于公司邮箱也要迁走。

## AWS 当前配置和数据边界

- 区域：Oregon，`us-west-2`；Ubuntu 24.04，实例 `seqforge-test-web`，4 GB / 2 vCPU，附加静态 IP。
- 应用：Docker Compose 运行 `seqforge-web:20261101-3` 和 Caddy；对外提供 80/443，SSH 限定管理员来源；3000 和数据库 5432 不公开。
- 数据库：独立、私有的加密 PostgreSQL 18.6，资源名 `seqforge-test-db`；应用通过严格验证的 TLS 连接。
- 当前发布目录：`/opt/seqforge/releases/20261101-3`；结果文件在独立的 `/srv/seqforge/seqforgebio/results`，不会因替换应用镜像而清空。
- Release-3 只更新首页标语、移除动效开关并将海豹改为静态姿势；基于 release-2 镜像发布，没有数据库迁移。Release-2 保留为可回退版本；后续修改下单逻辑等应用代码仍按下方完整构建流程发布。
- 日常实例备份保留七份，数据库备份保留七天。已验证一次受控重启后的自动恢复和私有存储持久性，但这不能替代备份恢复测试。

本地数据库与 AWS 数据库是两套独立数据。GitHub 不会同步客户、订单、管理员身份、专属报价、结果文件或浏览器草稿；这次也没有把开发电脑上的数据库复制到 AWS。真实客户历史数据需要另行制定导入、校验和回退方案。

密钥、SMTP/数据库凭据和运行环境文件由授权维护人员安全保管，不进仓库。Prisma 6 的 `sslcert` 在本部署需要匹配数据库证书链的**单一官方 AWS 根证书**；完整 CA bundle 另存。不要直接用多根 bundle 覆盖当前挂载证书，也不要关闭 TLS 校验。具体指纹与处理依据见英文运维手册。

## 设计伙伴怎样交付修改

1. 拉取最新代码，先读[总说明](../../README.md)、[设计文件地图](../../DESIGN_HANDOFF.md)和 [AGENTS.md](../../AGENTS.md)。本地启动见[换电脑指南](../../PC_HANDOFF_ZH.md)。
2. 公开营销页主要在 `public/brand/`；账号/订单/后台主要在 `src/app/`、`src/components/`。邮箱验证侧栏的动画是 `public/brand/verification-connection.js`，不要只改旧装饰 CSS 而漏掉实际组件。
3. 保留验证、草稿、价格复核、权限和列对应逻辑。视觉开发用本地邮件 preview；不要为了看效果向真实客户发信或伪造已验证状态。
4. 完成合适的代码/类型/布局检查。合成提交测试必须使用 `npm run test:smoke` 的隔离环境，不能进入本机工作队列或线上客户队列。
5. 提交清楚的改动说明并推送 GitHub，说明改了哪些页面、检查了哪些状态，以及是否涉及数据迁移。由维护人员审查后发布。

设计提交本身不会改动 GoDaddy、AWS 运行容器或公司邮箱。不要提交 `.env`、私钥、数据库转储、客户文件、个人合同、Windows 的 `node_modules` 或 `.next`。

## 发布新版本和日常维护

维护人员选择明确的源码版本，放入新的 Linux release 目录，使用锁定依赖构建**新的镜像标签**。先保留当前可用版本并备份数据库/结果文件；审查迁移后运行 `npm run db:deploy`，再切换 Compose 的镜像并检查 HTTPS、健康接口和关键页面。仅推送 GitHub、只改服务器源码文件或只重启旧容器，都不等于发布了新镜像。完整命令见[英文 runbook](README.md#updates-and-rollback)。

不要在 AWS 运行本地 `setup --seed-demo`、`migrate reset` 或复制开发数据库。不要用 `docker compose down -v` 清掉运行卷。失败时先判断新旧数据库结构是否兼容，不能随意恢复旧备份覆盖新订单。保留的 release-1 含已替换的依赖漏洞，不能作为回滚版本使用。

日常需要关注网站/健康接口、容器状态、磁盘空间、邮件失败、证书续期和备份成功情况，并核对账单/告警接收是否有效。数据库备份不含结果二进制文件，恢复时必须同时考虑二者。不要反复运行 `mail:test` 当作无副作用的健康检查，它会真实发信；也不要把“SMTP 已接受”写成“用户已收到”。

以后更换发件人/收件人可以独立修改服务器发信配置，不必迁移网站或收件邮箱。配置更新应由维护人员应用并重新验证；公司邮件域名的授权和 DNS 邮件记录仍需保持正确。
